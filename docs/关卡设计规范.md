# 关卡设计规范

这份文件给以后出题的人看——包括三个月后的你自己。照着它写，新关卡就能和现有的 15 关风格一致。

## 一、一个好关卡的标准

三条硬标准，一条不满足就别合进来：

1. **只教一个概念。** 玩家过关后能说出口的那个东西，必须恰好是一个。如果你要用两句话才能解释这关教了什么，拆成两关。
2. **broken 和 correct 的差异 ≤ 2 行。** 差异越大，玩家越是在"找不同"而不是在"想测试"。这个游戏练的是测试思维，不是大家来找茬。
3. **参考测试 ≤ 6 行。**（唯一例外：isolation 类要用两个测试函数暴露顺序依赖时，放宽到 8 行——目前只有 011。）一个 assert 能说清的，不写两个。玩家看答案是学思路的，不是抄代码的。

还有一条软标准：**broken 和 correct 的代码风格要一致**。一边 for 循环一边列表推导，玩家会以为"写法"才是问题所在。

## 二、六类教学点

分类不按 Python 语法（列表/字典/字符串），按**测试技能**。玩家做完 15 关，带走的是 6 个能迁移到真实工作的能力。

| 代号 | 分类 | 玩家学到 | 已有关卡 |
|---|---|---|---|
| `boundary` | 边界值 | 最大值在末位、空集合、单元素——错误最爱藏在位置的两端 | 001 差一 / 006 空集合 / 007 只有一个 |
| `exception` | 异常流 | 合法但罕见的输入（空、越界、类型不对）必须被想到 | 002 空 / 008 越界 / 009 错误的类型 |
| `isolation` | 状态与隔离 | 测试之间不能互相影响，单个过 ≠ 一起过 | 003 第二次 / 010 缓存 / 011 顺序 |
| `numeric` | 数值精度 | 浮点数不能直接 ==，整数除法会截断 | 004 相等 / 012 整数除法 |
| `contract` | 类型与契约 | 返回值类型必须稳定，None 必须被显式处理 | 005 两种答案 / 013 没有值 |
| `sideeffect` | 副作用 | 依赖当前时间、依赖字典顺序的代码不可测 | 014 今天几号 / 015 顺序不保证 |

每一类的判定标准和缺口：

### boundary（边界值）
- **定义**：bug 只在输入"位置特殊"时出现——开头、末尾、空、只有一个。
- **判定标准**：把触发 bug 的输入画在数轴上，它一定贴着某条边界线（0、1、n-1、n）。
- **还缺**：刚好等于上限的输入（"最多存 N 条"的 N 和 N+1）；下界之外的组合边界。

### exception（异常流）
- **定义**：存在一个合法但罕见的输入等价类，代码没为它安排出路。
- **判定标准**：输入分类画成等价类表格，至少有一格没人管（空、负数、带空格、类型不对）。
- **还缺**：空字符串 / 全空白字符串；"类型对但内容意外"（空文件、只有表头的 CSV）。

### isolation（状态与隔离）
- **定义**：被测代码带着跨调用的状态（可变默认参数、模块级缓存、全局列表），测试的执行顺序会改变结果。
- **判定标准**：同一个测试单独跑通过、和别的测试一起跑就挂，八成是这类。
- **还缺**：通过文件系统互相污染（测试 A 写的临时文件被测试 B 读到）；通过环境变量传递的状态。

### numeric（数值精度）
- **定义**：代码对数字做了数学上成立、计算机上不成立的假设（浮点精确、整除无损）。
- **判定标准**：找一个十进制下显然、二进制下不成立的算式（0.1+0.2、2/3）就能触发。
- **还缺**：浮点累加误差（sum 一列 0.1）；大整数转 float 丢精度。

### contract（类型与契约）
- **定义**：函数对"失败时返回什么"的约定被破坏，类型不稳定（有时 int 有时 None）。
- **判定标准**：只看返回值的类型/约定，不看具体数值，就能写出失败的测试。
- **还缺**：返回容器类型不一致（有时 list 有时 tuple）；布尔和 0/1 混用。

### sideeffect（副作用）
- **定义**：函数依赖外部世界（时间、随机数、顺序、环境），同样输入每次结果不同，原则上不可测。
- **判定标准**：问一句"同样的输入，两次调用结果一样吗"——不一样就是这类。
- **还缺**：随机数（random 没有种子）；环境变量 / 语言区域（locale）依赖。

## 三、YAML 字段说明

| 字段 | 写什么 | 不该写什么 |
|---|---|---|
| `id` | `999-name` 格式：三位数字 + 小写短横线名，编号 = 当前最大 + 1，同时是文件名 | 大写、下划线、中文 |
| `title` | 2-5 个汉字，玩家在列表里看到的名字 | 生僻词、英文 |
| `difficulty` | 1-5，判定标准见下一节 | 按代码行数定难度 |
| `tags` | **第一个必须是六类代号之一**（`check_levels.py` 的分类汇总按它统计），后面跟中文主题词 | 把分类代号放第二位之后 |
| `intro` | 期望行为，尤其是错误输入时应该怎样（返回 None？返回 0？） | 正确代码的任何片段 |
| `broken_code` | 一句中文注释指出可疑位置（学 001 的 `# 少遍历最后一个元素`） | 注释里写出正确写法 |
| `correct_code` | 和 broken 同风格、同命名的正确版本 | 顺手重构、改变风格 |
| `hints` | 1-3 条，从"往哪个方向想"到"具体试什么"递进 | 最后一条直接给答案 |
| `reference_test` | `from target import ...` 开头（判题器把代码写成 target.py 和测试放一起），≤ 6 行 | 凑数的 assert |

## 四、难度怎么定

难度不是"代码复杂度"，是**玩家需要几次失败的尝试**：

| difficulty | 定义 |
|---|---|
| 1 | 第一次提交就能过：触发 bug 的输入是日常直觉（最大值放最后试一下） |
| 2 | 换 1-2 个输入就撞上：知道要试边界，只是还没试对位置 |
| 3 | 要主动想到一个没试过的等价类（带空格、负数、第二组参数） |
| 4 | 要怀疑"测试本身怎么写"（调用顺序、共享状态、可测性），而不是怀疑数据 |
| 5 | 要先想清楚契约（返回类型、失败时的约定）再动手，数据反而很简单 |

当前分布：1×2（001、006）/ 2×4（002、007、008、012）/ 3×5（003、009、010、013、015）/ 4×3（004、011、014）/ 5×1（005）。加关时别让某一档空掉。

## 五、常见错误

1. **broken 和 correct 行为其实一样**——`check_levels.py` 会 FAIL。更早的办法：自己把两段代码各跑一遍。
2. **教的东西和别的关重复**——测试全绿也发现不了，加关前先看第二节的表。002（空列表崩溃）和 006（空集合边界）只隔一层纸，最容易撞车。
3. **参考测试过不了自己的关**——最常见原因：忘了 `from target import`；或断言写成 broken 也能过的形式（只断言类型、不断言值）。
4. **intro 泄露答案**——"空列表会导致崩溃"可以（指出场景），"应该先判断 if not nums"不行（给出代码）。
5. **broken 和 correct 风格差太多**——玩家会去找"写法差异"而不是想测试策略。
6. **参考测试贪多**——三个 assert 里两个是凑数的，玩家抄答案时抓不住主线。

## 六、新增关卡的流程

1. 想清楚这关教**哪一个**概念，到第二节查它属于哪类、这类还缺什么。
2. 写 YAML（照第三节），自己在 `_playground/` 人肉玩一遍：参考测试能过吗？假装不知道答案，能顺着 hints 走到吗？
3. 跑 `python scripts/check_levels.py`——全部 PASS 才算数。
4. 跑 `python -m pytest tests/test_levels_content.py -v`——内容质量的硬约束也要过。
5. 回来更新本文件第二节的表（已有关卡 + 还缺什么）。忘了这步，下一个出题的人就会和你撞车。
